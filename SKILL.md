# Luz Design

Luz Design owns how things look, how they are laid out and how they move: shared visual standards; the whole appearance of product front ends (admin consoles, mini-programs, websites, agent UIs) and of their interactive prototypes - composition, cards, the look of buttons and components, icons, images, motion, themes - drawn from the functional spec Luz-System writes (pages, entrances, tab bar items, components, button actions, flows); standalone visual work; and document layout. System decides what is on a screen and what it does; Design decides what it looks like and never adds, removes or re-orders pages, entrances, tab bar items, components or buttons - what cannot be drawn or laid out goes back to System ([ui-ownership.md](references/ui-ownership.md)).

## 调用协议（每次调用都按顺序做，不可跳过）

### 做界面项目先从这里开始

做后台、小程序、网站、智能体界面或可交互原型（整个项目或其中一部分）：

1. **先读规则卡 `design-path`**：`py -X utf8 scripts/context.py design-path`。它是从接收到交接的完整路径：十个阶段（P0 到 P9），每阶段有产出、检查和该读的规则卡，另附思考工具、常见失误与偏离说明的写法。规则分 must、default、hint 三档，must 不可偏离，其余偏离要写说明；它给的是思考顺序，不是死板模板。
2. **再按阶段读卡**：首页与常见页面的范式、入口归属与去重读 `page-patterns`；布局读 `interface-pattern`、`interface-layout`；视觉方向读 `design-direction`、`interface-visual`；组件库读 `interface-components`；图标、背景与卡片家族的细则（含图标颜色饱和度阈值）读 `interface-details`，图标尺寸与线宽读 `interface-icons`；做成产品开发用的前端界面 HTML（可点的单文件原型，多系统多页签）读 `prototype-reference`，原型参考实现与组件模板库只是参考，不是模板；动效读 `interface-motion`；价格、角标、券面等效果读 `interface-recipes`；素材读 `image-assets`。
3. **用这两个脚本**：`scripts/design_path.py` 管路径，`checklist --surface miniprogram|admin|website|agent` 生成可粘贴进会话 BRIEF 的检查表，`deviation <规则 id> --why … --risk … --verify …` 写标准格式的偏离说明，`show P0` 到 `show P9` 查某个阶段，`list` 看全貌；`scripts/page_pattern.py` 管首页与页面范式，拿到 Luz-System 的入口表 `entrances.json` 和功能清单后依次 `brief`、`plan`、做页面、`check`、`check-page`，`list`、`show`、`recommend` 用来查范式与推荐。Design 不增删功能与入口，要改的退回 Luz-System（[ui-ownership.md](references/ui-ownership.md)）。
4. **做成可点原型时再读 `prototype-reference`**：`py -X utf8 scripts/context.py prototype-reference`。什么时候整套用参考实现、只取一块、自己写，三栏单文件的形态，按编号取组件、`data-cid`、深浅色，规格与生成（`scripts/build_prototype.py <规格.json> --check|--out`，多系统 `scripts/build_prototype_suite.py`），验收（`audit_rendered.py --library luz-kit`，浅色与深色各一遍）和已知限制都在那里；页面清单与首页组成来自 System 的功能清单与 `page-patterns`，不从示例继承。
5. 下面的模式判定与前置检索照常先做；二者都不替代第 2 步起的规则卡。

**先判定模式与检索。** 若提供显式 project context / `LUZ_PROJECT_ROOT`，先按 [project-mode.md](../Luz-Project/references/project-mode.md) 读取 `project.py context <project> <stage> --skill luz-design`；项目阶段使用项目 HTML/JSON 与审批，不套 standalone 的旧会话路径。没有项目上下文就沿用本技能编号会话，不创建完整项目目录。

**项目模式下的界面文档。** design 阶段交给开发看的文档是 `docs/02-产品开发/02-前端界面设计.html`：先写前端架构（分层、页面地图、会话、路由与权限、状态、响应式、组件对照），再给每个系统、设备端（手机页、后台等）各一个页签，只放一个可交互原型（`03-手机原型.html`、`04-后台原型.html`同在 `docs/02-产品开发/`，不建子目录：真实页面重画、动效、场景配置面板、减少动态效果、手机宽度可操作），不放截图，路径与页面清单进“前端规范”，末尾写差异；章节与检查见 [dev-documents.md](../Luz-Project/references/dev-documents.md)。功能结构来自 System 的系统架构文档（前端页签）：本技能不增删页面、入口、标签栏项数、组件与按钮动作，发现需要改时退回 System（走需求变更台账）；本技能负责界面与原型的全部外观。原型动效取 `context.py interface-motion` 的令牌，原型页面用 `scripts/audit_rendered.py`（真实浏览器读计算样式：字号、对比度、斜体、字重、触控尺寸、`transition: all`、文本框聚焦框；浅色与 `--scheme dark` 各跑一遍）验收，`check_document.py` 看不到脚本生成的界面。

每次业务调用都按 [前置检索协议](../Luz-Crawl/references/preflight.md) 在方案/正式实现之前执行 `crawl_preflight.py run --caller luz-design --session <本技能会话或项目根> --topic <任务>`，已有任务加 `--task <任务目录>`，项目加 `--stage <阶段>`；阅读正文后 `conclude --file <补充信息.json>`，再 `check`。补充信息写回所属方案，结论交付 HTML；短任务也保留编号会话与检索结论 HTML。仅 doctor、空结果、手填 URL 或只读经验不算检索完成。不会为每条内部脚本命令重新建立任务。

Templates and builder scripts are the cheap path, and following them alone is how outputs miss the rules. They are skeletons. What a deliverable must look like comes from the rule pages, the user's preferences and past lessons, and the rule card puts all of that in front of you.

1. **Route.** Functional structure (pages, entrances, tab bar items, component list, button actions, flows, states), system architecture and hardware go to Luz-System; UI visuals, composition, component looks, icons, images, motion, themes and the look of prototypes stay here. Backend goes to Luz-Dev; prose to Luz-Writing; research to Luz-Crawl.
2. **Read the rule card before producing anything.** `py -X utf8 scripts/context.py list` shows the task kinds (xlsx, docx, reading-html, slides, pdf-markdown, showcase, poster, interface-visual, interface-layout, interface-pattern, interface-components, interface-motion, interface-icons, interface-recipes, interface-details, palette, design-path, page-patterns, prototype-reference). `py -X utf8 scripts/context.py <kind> [--topic 词 …]` prints the card: the user's preferences (all binding), matching lessons and facts, the rule text cut from the rule pages, the tools to use and the checks to pass. Read all of it. For anything the card does not settle, read the named rule-page section in full.
3. **Produce with the tools the card names.** Where a template or builder default differs from the card, follow the card. Re-read the named rule sections and `themes.json` for every deliverable; never ship a template's default palette and styles (check_document warns) or reuse the last project's look. Sessions get their card automatically: `new_session.py --card <kind>` saves it to `raw/00-rules/<kind>.md`.
4. **Record what you applied.** In the session BRIEF, `## 采用的规则` lists one row per rule section or preference key and how this work applies it; `publish.py` refuses a session without it, and validation flags a delivered file without it. Without a session, name the card you followed in the reply.
5. **Pass the checks on the card.** `make_xlsx.py` and `make_docx.py` run `check_document.py` on what they write and fail on any ERROR; `publish.py` runs it on the HTML it publishes; other files go through `check_document.py` by hand before delivery (PDF is checked as the card says, see Validate).
6. **Sediment — mandatory, checked at publish.** Every call writes or confirms at least one note with `experience.py note` and lists its key in BRIEF `## 本次沉淀`; `publish.py` refuses a session whose listed keys are missing from `experience/notes.json` or were last confirmed before the session started. Without a session, run the note command before replying. What to record is in 每次调用后沉淀.

## Not this skill — route instead

**Interface rules are split between the two skills.** [ui-ownership.md](references/ui-ownership.md) is the one source; summaries elsewhere defer to it. Luz-System decides what is on a screen, what it does and how the user moves through it; Luz-Design decides what it looks like, how it is laid out and how it moves.

| Matter | Luz-System decides (function) | Luz-Design decides (looks) |
|---|---|---|
| Pages, entrances, tab bar, navigation | which pages; how many entrances and where each goes; tab bar items, names, order; menu groups | how entrances are laid out (grid or list, columns); tab bar height, icon glyphs, selected style; sidebar width |
| Components and buttons | which component does which job; what each button does, when it is disabled and why, results, feedback, undo, permissions | library and theme; look, size, radius, colour; hover, pressed, disabled and loading appearance |
| Cards, lists, tables, charts | what a card carries and in which order; columns, default sort, filters, pagination, bulk actions; which question a chart answers | composition, hierarchy, radius, stroke, shadow; column widths, row height, header style; chart colours, line width, grid, tooltip look |
| Images, icons, motion, themes | which objects need an image or an icon; what must not jump; undo windows; whether an appearance setting exists and where | image style and content, glyphs, line width; animation shape, duration, easing; light and dark values, contrast |
| Responsive, prototype | which functions stay on a narrow screen; actions, pages, states, demo data, scenarios | breakpoints, grid, spacing; the whole look of the prototype |

Two lines are never crossed. System does not pick colours, sizes, radii, shadows, icon glyphs, image content, grid values or animation timings - its rule pages say "see 视觉设计规范 …" instead. Design never adds, removes or re-orders pages, entrances, tab bar items, components or buttons and never changes flows, states or copy keys; when something cannot be drawn or laid out it goes back to System (project mode: the requirement-change ledger). Function wins over looks: if a look makes a function unusable, keep the function and change the look. Time splits the same way: a toast gone after 3 s, an undo window of 5 s, a skeleton after 1 s are behaviour (System); how long an animation runs and its easing are looks (Design).

Behaviour rules stay in [ui-standards.html](https://github.com/luzern0414/Luz-System/blob/master/references/ui-standards.html) and the surface pages (local: `D:\Codes\Luz-System\references\`). The numbers of how it looks live here only: visual-design.html 一、视觉基础 (type, colour, icons, radii, elevation, motion) and 二、排版基础 (界面组件的外观, 同类元素外观一致, 界面配图与丰富度, 前端排布的推导, 各端视觉参数, density and table alignment). `new_session.py` refuses the system, prototype and hardware session modes (their session engine is Luz-System's); the look of a product interface or prototype is worked from the interface rule cards.

## 自适应界面视觉匹配（界面任务新增阶段）

参考案例是证据，不是模板。遇到用户给出“5×2 图标”“2×2 指标”“三列杂志”“毛玻璃/软糖/2.5D”等示例时，先读取 [layout-inference.md](references/layout-inference.md) 和 [interface-style-matrix.json](references/interface-style-matrix.json)，运行 `py -X utf8 scripts/style_match.py`，把信息拆成三层：

- **证据层**：保留参考中的关键词、数量、排列、材质和动效，写入 `evidence`，用于解释候选；不要把数字直接变成 CSS 或页面固定结构。
- **语义约束层**：保留用户明确提出的内容关系、优先级和可读性要求。用户写明“非对称指标看板”时，必须保留主指标锚点、辅助指标和独立信息面板三种关系；具体放置、列数、跨度和移动端折叠由内容和视口决定。
- **决策层**：根据真实对象数量、文本长度、图片比例、交互强度、优先级、可用宽度和断点推导区域、列数、比例、堆叠顺序与图标角色；在 `decisions`、`adaptation` 中写清原因。相同 brief 在桌面和移动端应得到适配后的不同参数。

参考数字只有在用户明确写出“必须、固定、严格使用、不可调整、锁定、强制”时才进入 `layout.hard_constraints`。否则“5×2”只是一个候选排列信号，服务图标可按卡片最小宽度和视口得到 3 列、4 列或其他结果；“2×2”同样不能自动限制辅助数据看板。不要为了复刻参考图添加空卡片、空列或装饰面板。

匹配器输出 2–3 个风格候选及其理由、适用角色和无障碍风险；MorphIcons、Lordicon、Hover、Loop、Spring 等动效参考写入 `evidence.motion_signals`，再转成需确认的状态反馈、形变或循环候选。控件图标、导航、标签、菜单、按钮、工具栏、表格和表单仍是统一 2 像素线性矢量；候选风格默认只可作用于入口图标、指标图形、空状态、品牌主视觉和装饰元素。毛玻璃、黏土、软糖、2.5D、拟物纹理等不能自动改成全局页面风格。

### 用户确认门

匹配结果默认 `approval.status = "pending"`。在用户确认选中的风格和作用范围前，只展示页面意图、语义关系、自适应布局方案、2–3 个视觉候选、影响范围和风险；不调用 Imagegen，不正式生成资产，不修改页面代码，不发布。确认后将 `status` 改为 `approved`，并保留 `scope.controls = "line-vector"`，再进入具体视觉设计或实现。

匹配结果统一保存在 `raw/02-visual/style-match.json`，approval 记录 approved_by、approved_at 和 note（用户原话/确认依据）。带 interface-visual 规则卡的会话在 document 模式发布时也检查这项确认。

## 每次调用后沉淀

Mandatory on every call, not only for sessions. Every call leaves at least one note behind — new or confirmed — and a session lists those keys in BRIEF `## 本次沉淀` (| 经验 key | 类型 | 一句话 |); `publish.py` checks them. Record, among others:

- **preference** — what the user stated or corrected this time (a colour, a size, a layout habit, something they dislike).
- **lesson** — a rule correction, a mistake the checks did not catch and the right way, a template default that had to be overridden.
- **fact** — a design approach that worked (palette and the steps used, type scale, layout, which component library and component was referenced), research sources and scope (which sites or documents were useful or useless, the queries used), generation parameters (Imagegen prompt block, sizes).
- **Already known and used again** — write the same key again to confirm it (`uses` +1); when the new finding contradicts it, rewrite the same key and the old text becomes `previous`. Never add a second note on the same topic.

One store, `experience/notes.json`, with the same shape and commands in Luz-System, Luz-Design, Luz-Dev and Luz-Writing:

- **Start:** `py -X utf8 scripts/experience.py search <关键词> [--kind preference|lesson|fact]` and apply what matches.
- **Before finishing:** `py -X utf8 scripts/experience.py note --kind preference|lesson|fact --key <主题> --text "<一句话原则>" [--why "<依据>"]` — the general principle, not task trivia.
- **Fields:** `key`, `kind`, `text`, `why` (optional), `uses`, `first_seen`, `last_confirmed` (YYYY-MM-DD), `previous` (`{text, replaced_at}`, only after a replacement).
- **Replace, never pile up:** the same key replaces the text (one `previous` kept, `uses` +1); the same statement under another key confirms that note. Caps: preference 60, lesson 120, fact 120; over a cap the fewest uses, then the oldest confirmation, go first. `list [--kind]` shows notes; `prune` enforces caps and lists notes unconfirmed for 180 days; `check` fails on duplicate keys or statements, missing fields, overflow and private data.
- **Scope:** a preference prints on every rule card, so a preference that holds only for one kind of product says so in its text and points to the theme or rule that carries the details (for example a theme in `themes.json`).
- **Public repository:** no phone numbers, emails, WeChat IDs, user-home paths, credentials, personal, client or project names; `note` refuses the detectable ones.
- **Tests and rehearsals only:** `LUZ_EXPERIENCE_STORE=<path to a notes.json>` points `note`, `list`, `search`, `prune`, the rule cards and the 本次沉淀 gates at that file for the whole process and leaves the skill's own notes and catalog untouched; the gates print a reminder while it is set. Real deliveries never set it. A program that calls the skill on behalf of clients writes generic notes after approval, searches first and confirms an existing key rather than adding a new one, and never records client context.

Here also: curated palettes, type scales, visual and file rules with sources go to `patterns.json` through `experience.py add <file.json>` (kinds 色彩, 字阶, 视觉规则, 文件规则, 设计理念, 调研经验; cap 200); `catalog.md` is re-rendered after every write.

## Output baseline

Each line is a summary; the rule page section named in brackets is the rule.

- **First line is the title** (visual-design.html 文字纪律 › 第一行就是主标题): no subtitle, summary, tags, timestamps, tool names, source counts, hashes, file paths or design notes; apply the deletion test to every visible element, by problem family, not by word list.
- **Colour** (配色, 主题色系统, 取色依据, 深色与浅色两套主题): every product front end (admin, mini-program, H5, website, agent UI, and their prototypes) ships a light theme (the first set; design and acceptance start from it) and a dark theme (the second set, from `themes.json` `dark` and `shared.dark`: darker ground, lighter foreground, raised surfaces lighter, never an inversion), follows the system appearance by default and offers a manual 跟随系统 / 浅色 / 深色 switch; reading pages, posters, slides and files are documents and stay light, printed light. Light surfaces in the light theme; one primary from the industry's mood (`themes.json`), taken from one column of an official 10-step palette; 60-30-10 with neutrals dominant; product UI adds at most one marketing accent, one fixed accent per top-level module, the shared price colour and one solid brand card per screen; no gradient buttons; `check_contrast.py` and `check_document.py` enforce it.
- **Type** (字体与字号, 七级字体角色, 小程序字阶): one font stack `"PingFang SC", "Microsoft YaHei", "Noto Sans SC", system-ui, sans-serif` in HTML and Microsoft YaHei in files. Chinese PDF export sources explicitly use `"Microsoft YaHei"` for titles, headers, body, Latin text and page numbers; verify the actual embedded PDF faces are MicrosoftYaHei / MicrosoftYaHei-Bold. A formal Word document (client proposal, manual, contract, official paper) follows its own standard: 宋体 or 仿宋 and 黑体 or 楷体 for Chinese, Times New Roman for letters and digits. `check_pdf.py` adapts to the document (`--fonts auto`): it accepts either family for what it is and refuses a document that mixes them or that carries a fallback face. User-specified fonts follow the request (`--fonts NAME`). Weights 400/600/700 with 700 only at 22px and larger; nothing below 12px in HTML (websites and reading pages 14); no italics, letter spacing or rotated text; every size comes from the scale of its product type. Chinese typesetting (中文排版): `lang="zh-CN"`, no closing punctuation at a line start or opening punctuation at a line end, dash and ellipsis never split, lines of about 40 characters (at most 48), line height 1.5 to 2, no hand-typed spaces between Chinese and Latin text; which punctuation to use is Luz-Writing's.
- **Contrast and accessibility** (主题色系统 › 对比度算法与等级, 点击区域与触控目标, 视口、安全区与自适应写法): ratios are WCAG 2.2 (relative luminance with the 0.04045 threshold, never rounded up): body text 4.5:1, large text and controls 3:1, this skill's body ink 7:1; APCA belongs to the WCAG 3.0 draft, whose contrast algorithm is still undecided, so it is never a pass basis. Touch targets 44 × 44 (desktop pointer at least 24, spacing exception of WCAG 2.5.8); every page declares the viewport without disabling zoom; edge-to-edge pages use `env(safe-area-inset-*)`; mini-programs take the safe area from `wx.getWindowInfo()` and the capsule from `wx.getMenuButtonBoundingClientRect()`; animation has a `prefers-reduced-motion` branch. Each theme's dark mapping passes `check_contrast.py` (body ink 7:1, secondary 4.5:1, brand text and status text 4.5:1 on every dark surface, white on filled brand and status colours 4.5:1), and a page is audited in both appearances with `audit_rendered.py --scheme light` and `--scheme dark` (深色与浅色两套主题).
- **Front-end components** (组件与组件库): every front end picks one component library from `references/component-libraries.json` before design starts, and every control (buttons, forms, tables, dialogs, navigation, tags, steps, drawers …) is a real component of that library, re-coloured through the library's own theme mechanism with the theme library's tokens. Hand-written HTML/CSS controls, a page that only loads the library's style sheet, and whole pages written directly by the model are not delivered; custom work is limited to layout, theme tokens and business blocks assembled from the library's atoms. Pages ship a light theme (theme canvas, white cards) and a dark theme (the library's own dark mechanism plus the theme's `dark` mapping, kept in step with the page's `data-theme`) with restrained, premium colour. `audit_rendered.py --library <id>` reports hand-written controls and a page showing fewer than 6 of the library's components.
- **Graphics and depth** (扁平线性风格, 图形：一套线性图标, 插画：多层扁平, 层级与立体感): control icons are 2 px line vectors (1.75 at 16 px); entry icons, illustrations and decorative elements are duotone line, layered flat or generated in the one style the user picked; depth belongs to surfaces only, from the five elevation tokens in `themes.json` `shared.elevation`; one object, one icon. Focus (边缘线条) is a prohibition: a focused or clicked text field (input, textarea, select, library fields such as `el-input`, `el-select`, `van-field`) only deepens its 1 px border to `ink2` — no blue or primary frame, glow, thick outline or browser default outline; buttons, links, tabs, checkboxes and switches show a 2 px dark outline (`ink`, offset 2 px) on `:focus-visible` only, never on a mouse click and never in the primary colour; mobile pages set `-webkit-tap-highlight-color: transparent`; `audit_rendered.py` reports a violation as 聚焦框.
- **Tables** (界面密度与表格对齐; file-design.html 表格文件): header centred, long text left, short values centred, amounts right-aligned with tabular figures — in interfaces, reading pages, Excel and Word alike (a formal client document and the architecture atlas keep headers over their own column: text left, marker columns centred, amounts right). The table reads as centred overall: columns fit their content, every cell is vertically centred, and when columns are wide or equal, left-aligned text sits as a block in the middle of its column; Chinese cells break only between words, with balanced line lengths.
- **Table PDFs** (file-design.html 网页文件 › 组件, 便携式文档): catalogues and lists in landscape — build with `make_table_pdf.py spec.json out.pdf`. Choose `theme` explicitly for this document's subject; never use one palette for all files. Write each item individually, without a common character or line limit. Main, section and industry-group headings share the left margin. Real row heights drive pagination; every physical fragment has a repeated header and all four corners rounded (12px), including bottom edges and continuation pages. Check domain word breaks with `keep_together` and rendered pages. The builder verifies source HTML, embedded YaHei fonts, text, bookmarks and `max_pages`, and saves layout evidence and overview images. Any finished PDF, from this builder, from Word or from a poster, goes through `py -X utf8 scripts/check_pdf.py <file.pdf>` (embedded fonts and family, text layer, bookmarks, page size; `--accessible` for tags, language and title; `--print` for bleed boxes, 300 ppi and RGB images).
- **Spreadsheets** (file-design.html 表格文件, 导出文件): build with `make_xlsx.py spec.json out.xlsx`; the look is fixed: 宋体 (Microsoft YaHei on request, one family per workbook), body 12 pt, title body + 4 pt bold centred on the header blue-grey, every text black, colour only as pale fills — `tint_by` gives each category of one column its own pale fill (six in turn, neighbours differ), `highlight` paints the rows that need a second look amber, and the subtitle says what the colours mean; group names centred and merged vertically, tag values bold via `tags`, numbers right-aligned (`days` 0.0, `money` #,##0.00), sub-totals on the pale band and the grand total on the header colour via `footer`, thin black borders, no gridlines, landscape A4 one page wide for wide tables with repeated header and a 第 N 页 / 共 N 页 footer. No sequence column; one fact per cell; system exports are cleaned business tables, not database dumps. `check_document.py` reports clipped text, foreign fonts, fonts under 10 pt, mixed alignment and badly ordered grouping columns.
- **Documents for a client are not showcase pages.** A proposal or manual is a Word document (file-design.html 文字文档 › 客户正式文档): `make_docx_paginated.py spec.json out.docx` writes the .docx and the PDF exported from it — cover, clickable contents, 一、（一）headings without parentheses, header title, centred page number, black and white, every table titled above and continued under 续表 N. Feature list, quote, rule collection and ledger are Excel. The architecture atlas is a PDF in `style: atlas`. Read `context.py docx` before any Word or PDF; search only for what the card lacks.
- **Architecture atlas** (file-design.html 系统架构图册): `make_showcase.py spec.json out.pdf` with `"style": "atlas"` — layered architecture / swimlane / deployment figures and titled tables only; one ink for every word, regular weight only, hairlines and a pale table head instead of black frames, no title in the page header and none on the first page (`"show_title": false`; the title stays in the file name and the PDF properties), a centred page number; pages packed so sections share them (a page under 70 % full is an error).
- **Slides** (file-design.html 演示文稿): 16:9 (13.333 × 7.5 in), light backgrounds, 40/28/20/18 pt, one conclusion per slide in the title placeholder with a title of its own, margins of at least 5% of the width, alternate text on pictures, header rows on tables; `check_document.py` checks all of these.
- **Word** (file-design.html 文字文档, 按文档类型, 论文版式): build with `make_docx.py spec.json out.docx`; decide the document type first (contract, proposal, report, minutes, general; `"style": "paper"` only when the user asks for the paper text rules; GB/T 9704 only when asked).
