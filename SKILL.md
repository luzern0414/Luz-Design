# Luz Design

Luz Design turns a scoped request into an auditable frontend design session: what users see and how they interact. Backend behavior, APIs, data storage, payments, regulations, and compliance implementation belong to the sibling Luz-Dev skill and are never researched or designed here.

The rules are layered: [design-standards.html](references/design-standards.html) holds what every surface shares, ordered from design architecture down to copy, and its sixth layer (视觉基础) is the visual baseline for every output including documents and posters. Each surface page repeats the same seven layer headings and holds only that surface's specifics; a surface page may tighten a common rule but never relax it, and where it is silent the common rule applies. Design top-down: a layer is settled before the next one starts. The rule pages define standards and judgment, not templates: derive color, composition, and structure from each request. Read [WORKFLOW.md](WORKFLOW.md) for phases and stop conditions, and [experience/catalog.md](experience/catalog.md) before researching.

## Output baseline

- The first visible line of every HTML, Markdown, Word, PDF, spreadsheet, or slide deck is the main title; the first section starts directly below it. No subtitle, summary, tags, timestamps, tool names, source counts, hashes, file paths, or design-reference notes anywhere.
- Apply the deletion test (design-standards.html, 文字纪律) to every visible element. Problems are families, not word lists: anything about the output itself, reading guidance, repetition, asides, unrequested advice, pleasantries, placeholders, and self-evaluation are removed in whatever wording they appear. Verbatim third-party text is quoted, not rewritten.
- Interfaces show only product functions and the system's own data. Strategy, advice, plans, playbooks, "recommended" campaigns, rollout rhythms, best-practice tips, or explanations of how the business should operate never appear as cards, banners, or text inside an admin console or mini-program, even when research produced them; research conclusions stay in `raw/` documents. Form help text only states a field's constraint or effect in one short line, and footnotes that re-explain the page are removed.
- A redesign of an existing product keeps exactly the existing function set: every page, field, action and metric must map to an existing interface or to a function the user explicitly asked for. Never add modules, cards, KPIs, to-do lists, readiness checklists, batch actions, analytics, campaign types or settings on your own initiative, even when research suggests them; list such ideas for the user outside the interface instead.
- No explanatory text in product interfaces: no help lines under inputs, no footnotes, no rule explanations (pricing order, stacking, auto-calculation, sync behaviour), no consequence paragraphs in confirmations. A confirmation is a title naming the action and object plus the inputs it needs (amount, reason, password, typed check) and the action buttons. Field labels, placeholders, status tags, counts and error messages are the only words.
- Use the real brand and scope the user gives: the brand name appears in the browser title, login page and top bar; a single-store business never shows store switchers, "new store", store numbers or multi-store wording.
- Manual money operations (recharge, adjustment, refund amount) use a free amount input with two decimals, never fixed preset tiers, unless the user asks for presets.
- Common controls follow the mainstream pattern users already know (research it with LuzCrawl before drawing): password fields carry an eye icon button inside the right edge that toggles visibility, has no text, is named "显示密码 / 隐藏密码" for assistive technology and switches to a crossed eye; icon-only buttons carry a tooltip and accessible name; the account menu sits under the avatar with 修改密码 and 退出登录; search shows a magnifier and filters while typing.
- Every chart shows an immediate custom hover tooltip (date or category, each series with its colour dot, value with unit), with a crosshair or highlighted segment; native SVG <title> tooltips do not count. The browser test hovers each chart and asserts the tooltip.
- Login pages use a real generated photo or a flat line illustration of the business beside the form on desktop and as a top banner on phones; never leave a blank or abstract placeholder panel.
- Every admin list whose records carry a time (members by registration, orders by order time, coupons by issue time, participation records, logs, feedback) has a date-range filter: quick ranges 今日 / 近 7 天 / 近 30 天 / 全部 plus custom start and end dates, combined with search, segment and header filters. Above the table a row of statistic cards summarises the whole filtered set, not the current page (members: count, valid cards, inside, stored balance; orders: count, received, refunded, pending; coupons: issued, used, available, expired). In the implemented system these figures come from a backend aggregate over the same filters.
- A delivered system shows only live data from the backend database: no hard-coded demo rows, sample numbers, placeholder devices or static charts. Prototype data stays in the prototype; implementation pages render loading, empty and error states from real API results.
- Dashboard cards and charts show only metrics the existing backend already returns (or the user requests); never add rankings or breakdowns such as staff performance that the product does not record.
- Light surfaces only, one accent color plus neutrals, one font family per file.
- Choose the primary colour from the industry's mood found in research, never by habit (references/themes.json holds industry themes; a gym is energetic orange with gold for marketing, not teal). Pair colours by harmony (design-standards.html: 配色和谐): marketing takes an analogous hue of the primary and is told apart by tinted containers, a complementary hue only for small contrast; never put two saturated hues of similar chroma side by side (saturated orange next to saturated violet); buttons use the darker shade (white text ≥ 4.5:1), graphics the brighter one; one chart series is emphasised. Two font weights only (400, 600), no letter spacing, no rotated or skewed text (stamps and badges stay level); images in one group share one aspect ratio and are cropped to fill.
- One object, one icon (design-standards.html, 图形：一套线性图标): different objects never share a pictogram — 每日抽奖 a prize wheel, 新人礼券 a gift box, coupons a ticket, winning records a trophy, month cards a calendar, count cards a tally card, area an area frame — and the same object uses the same icon everywhere; generic glyphs (back, arrow, close, check) are exempt; never hang one generic icon (settings, document, star) in front of several different headings, leave the icon out instead. `check_document.py --allow interface` flags one drawing labelling different things; for script-built prototypes also list each page's icons and labels in the browser.
- One typeface everywhere (design-standards.html, 字体与字号): every HTML page, prototype, rule page and template declares the same stack in the same order — `"PingFang SC", "Microsoft YaHei", "Noto Sans SC", system-ui, sans-serif` — with no Latin display font, serif, KaiTi or rounded face added; documents, spreadsheets and slides use Microsoft YaHei. No text below 12px in any HTML (interfaces and agents 12, websites and reading pages 14), including SVG labels, inline styles and text built in scripts; `check_document.py` checks all of these.
- Type scales differ by product (design-standards.html, 字阶): reading HTML 14/16/20/24/32; spreadsheet 12 with an 18 pt title; a product deliverable (function list + mini-program + admin in one page) uses one family and one scale for all three parts: 12/14/16/18/22/28, page title 32, one line height per size, body 14; Word 10.5/12/14/16/22 pt; slides 16/20/28/40 pt. Use only those steps. Never italic: Chinese has no true italic, so emphasis is weight, colour, or position. Every element, including inputs and chart text, inherits the family explicitly; chart text is counter-scaled so it renders at 12 px whatever the chart width.
- Center the composition: page containers are horizontally centered with a max width; groups of panels (a phone frame with its controls, a pair of columns) are centered as a whole.
- Word documents (file-design.html, 文字文档 and 按文档类型): build them with `py -X utf8 scripts/make_docx.py spec.json out.docx` (type contract / proposal / report / minutes / general, title, sections with paragraphs, items, tables and children, attachments), then run `check_document.py`. A4, Microsoft YaHei, title 22 pt, headings 16/14/12, body 12 pt at 1.5 lines, tables 10.5 pt with a pale header that repeats, nothing below 10.5 pt. Contracts: title, contract number, each party's name, credit code, domicile, representative and contact, one preamble paragraph, clauses numbered 第一条 / 1.1 / 1.1.1 covering the Civil Code Article 470 terms (parties, subject, quantity, quality, price, time place and manner of performance, liability for breach, dispute resolution) plus what the deal needs, money written as 人民币 128,000.00 元（大写：壹拾贰万捌仟元整）, “（以下无正文）” then a two-column signature block, footer “第 X 页 共 Y 页”, attachments on new pages, no 【请填写】 or ×× placeholders. Proposals: 一、（一）1.（1） numbering, background and goals first, plans, roles, budget and acceptance as tables, totals that agree everywhere. Reports lead with conclusions; minutes end with a decisions table (item, owner, due date). Official documents (公文) follow GB/T 9704 only when the user asks for that format.
- Spreadsheets (file-design.html, 表格文件): build them with `py -X utf8 scripts/make_xlsx.py spec.json out.xlsx` (title, columns with types and merge flags, rows, optional total) instead of hand-styling, then run `check_document.py` on the result. One worksheet unless the user asks for more; title row, header, data; nothing outside that rectangle. Microsoft YaHei only, title 18 pt and everything else 12 pt, never below 12. No sequence-number column. A grouping name (category, subsystem, region, store, month) repeated down consecutive rows is merged vertically into one cell, child groups only inside their parent; no horizontal or block merges in the data; one fact per cell, so compound cells are split into columns or rows. Light colour for readability: pale blue header, first-level group cells rotating through step-1 tints of the official palette, alternating white and very light grey per group, light grey total row, thin light-grey borders, dark text. If the user says the sheet will be filtered, sorted, imported or read with a screen reader, do not merge; write the group name on every row instead.
- Product colour comes from standards, not taste (design-standards.html: 取色依据; research official palettes with LuzCrawl first): 60-30-10 with neutrals dominant; brand, hover, pressed and tint steps from one column of an official 10-step palette (Ant Design, TDesign), the brand step being the first that gives white text 4.5:1; one solid primary button per screen, secondary and marketing actions as tinted containers with same-hue text; active controls and chart series at least 3:1 against white (WCAG 1.4.11), no half-light pastel fills, no gradient buttons; charts use one step across hues with grey for "other". `check_contrast.py` and `check_document.py --allow interface` enforce it.
- Avatars (design-standards.html: 头像): show the uploaded photo; otherwise a default cartoon animal picked by a hash of the user id, the same animal everywhere; a line icon only for logged-out or system users. Never initials, surnames, nickname fragments, ids, any other text, or emoji characters; `check_document.py --allow interface` rejects text inside avatars.
- Product interfaces are flat and line-based (design-standards.html: 扁平线性风格, 图形：一套线性图标, 风格依据; NN/g flat design, Material 3 / Atlassian / Ant Design elevation, Ant Design and Lucide icon rules, chartjunk): one set of stroked line icons on a 24 grid, one stroke width (1.5 px, non-scaling) with round caps, coloured like the adjacent text; emphasis comes from a tinted rounded block behind the line icon, never from 3D, glossy, multi-colour filled or image-generated icons; illustrations are dark-grey line drawings on white with at most one accent; pages sit on a very light neutral grey, cards are white with the lowest elevation shadow (slight float), overlays one level higher, neutral shadows only; card radius 12, inputs and buttons 8; no decorative gradients, textures, glass, organic blobs, bevelled or glowing buttons — only photo scrims and skeleton shimmer may use a gradient. Admin: every side-nav item has a 20 px line icon and every page- or card-level function button a 16 px one (dialog footers excepted); line charts are smooth 1.5–2 px curves without gradient fill, horizontal gridlines only in the lightest grey. Still give every entry, title, list item, button, benefit, and status a graphic, use real-looking photos for stores and products, and show photos, icons and key numbers together on home, detail, and profile screens. `check_document.py --allow interface` rejects gradients, SVG gradient fills, bevels, glows, heavy card shadows, blur glass, blob radii and mixed icon stroke widths.
- Classify every function before placing it (design-standards.html, 入口与内容分层): core tasks (tab bar or fixed first-screen spot, primary colour, never hideable), status and information (neutral, right after core), marketing (time, stock or audience limited; after core, at most 2 on the first screen, one slot per campaign, auto-collapses when ended or claimed), auxiliary (lists in 我的 or detail pages). One destination has one entry per page, and one fact is said once per card and once per page.
- Mini-programs follow miniprogram-design.html: core tasks own the tabs and are not repeated on the home page; the home page is brand or store (core) → live information → marketing; only the tab bar switches tabs; every tab keeps its own stack; secondary pages return to the page that opened them; modules are typed core, information, or marketing, and only the last two can be hidden.
- Admin consoles follow admin-design.html: the data cockpit is the first menu and is ordered by value — business results (revenue, orders), then growth (new members), then activity (visits), then efficiency, risk and negative data (refunds, failures, complaints) last; within a group, metrics that move and need action come first and long-flat ones (a pass rate stuck at 96–98%) go last; rankings and shares sort descending; negative data is never hidden but sits in a later 风险与异常 slot, with a dismissible alert on top only when it crosses a threshold; menu group titles are bold with a divider and a short neutral bar, menu items regular with a line icon each; table headers and short cells (numbers, money, status, dates, IDs, actions) are centred, only wrapping long text is left-aligned; grids shrink so nothing is clipped at 1280–1920 px; details, edit forms and confirmations open as a centred floating panel (never a right-docked drawer) so the visual centre stays in the middle; low operation cost — status fields are inline switches, search filters while typing, every enumerated column filters from its header, row actions open their target directly, and only important changes (take down, disable, freeze, pause, reprice, refund, delete) get a centred confirmation while turning things on is one click; composite cells and cards are "centred, then left-aligned" with equal widths and heights, card content fills or centres in the card, KPI labels are 16 px/600 next to a 32 px icon tile; configuration closes the loop — list every piece of mini-program content with its source (admin config, system computed, user generated), give every admin-configured item full maintenance (add, edit, delete or disable, reorder, show/hide; photos upload, delete, cover, caption), keep one copy of the data and never hard-code operating content in the mini-program; restrained colour.
- Agent UIs follow agent-design.html: write the task goal, tools with the objects they read and write, and stop conditions first; tools are tiered by impact — read-only runs directly, reversible writes run and offer undo, irreversible, money-moving or outbound actions stop at an approval card (批准 / 修改 / 拒绝 / 我来处理); every tool call is a collapsible card in business words; output streams and can be stopped; failures state the cause and what was already changed, never retried silently or shown as done; no model names, internal reasoning or function names on screen; single 760 px conversation column, user messages light grey on the right, agent replies without bubbles.
- Websites follow website-design.html: each page has one main action; the first screen says who you are, what you offer and the next step, with a real photo and no auto carousel; top navigation of 5–7 items in visitor words, expanded on desktop and in a menu button on phones, current page highlighted, a footer with contact, legal and filing info; Material breakpoints 600 / 840 / 1200 / 1600 with content at most 1200 wide and reading text at most 720; type 16 body, 40 first-screen title (28 on phones); content comes from the back office; every page has a title and description for search; Core Web Vitals targets (LCP 2.5 s, INP 200 ms, CLS 0.1).
- Function lists follow function-list-design.html: columns 模块, 编号, 端, 功能, 所在页面, 关键交互, 界面状态; module and state cells merged per module; one size and weight for all body cells; headers and short columns centred.
- Same-category elements are equal in height and identical in parameters (design-standards.html, 同类元素一致); motion follows one system (design-standards.html, 动效): push slides in, back slides out, tab switches fade.
- When the user asks for a real or commercial (商业版) system, the delivered interface has no prototype configuration panel and no simulation switches: it starts at a login page, uses the product's existing account system unchanged, and outcomes come from real data and API results. Otherwise, the prototype's configuration panel is grouped by tab (admin: by menu) plus 全局, with page shortcuts, module switches, and every business outcome listed separately (system-design.html, 原型配置面板). Pre-render JS panels into the delivered file.
- Delivered pages work on a 390 px phone (system-design.html, 手机上可操作): fixed-height mini-program frame, admin menu in a drawer, tables become labelled cards, no horizontal page scroll. Verify at desktop and phone width in a real browser.
- Product interfaces isolate page purposes (design-standards.html, 信息架构): personal data lives under 我的. Mini-programs include login authorisation with agreement consent, user agreement, privacy policy, separate consent for biometric data, purchase terms before payment, and privacy settings.

## Common control patterns

Researched with LuzCrawl across Ant Design, Arco, TDesign, Element Plus, Semi, Material 3, Apple HIG, Atlassian, Carbon, GOV.UK, Nielsen Norman Group and Baymard (2026-10-27; evidence in session 002 `raw/01-system/common-ui-research.md`). Admin and mini-program surfaces follow these unless the user decides otherwise.

- Login: centred card, or image left and form right with the image as a top banner on phones; logo and system name above the form. A failed login always says 账号或密码错误 at the form, without telling which field was wrong. Submitting shows a loading state and ignores repeat clicks. Passwords stay hidden by default behind an eye icon button with no text (see Output baseline); use autocomplete current-password or new-password, allow paste, and set no maxlength.
- Inputs: a persistent label on every field; placeholders only show examples. Required fields carry a red asterisk before the label. The clear button appears only when the field has content. Fields with a length limit show 已输入/上限. Validate on blur; once an error shows, re-check on every keystroke and remove it as soon as the value is valid. Errors sit under the field in red with a red border, say how to fix it, and never clear what the user typed. On submit, focus the first error.
- Search: magnifier icon on the left and a specific placeholder; filters while typing (debounced, with a loading state); Esc clears; never show 暂无数据 before the request returns.
- Lists: title, then toolbar (search and filters on the left, the primary button on the right), then table, then pager. Sort arrows show only on sorted columns; filter icons sit right of the column name. Row actions go in the last column: two shown as text, more in a 更多 menu. Batch selection uses a first-column checkbox with a half-selected header and a 已选 N 项 bar. The pager sits bottom right: 共 N 条, page numbers with ellipsis, page size and jump. First load uses skeleton rows. Headers stick on long tables, and long cells truncate with a tooltip.
- Switches only for settings that take effect immediately; they show loading while switching and roll back on failure. Forms that need 保存 use checkboxes. One primary button per area; levels are primary, secondary, text and danger. Danger entries are plain or text buttons, and the red button appears only inside the confirmation. Button text starts with a verb and names the object. Icon-only buttons have a tooltip plus an accessible name.
- Dialogs: centred, with a mask, a top-right close and Esc. Read-only dialogs close on mask click; dialogs with forms do not. Footer buttons sit on the right with cancel left of the action, and the action is named (删除, not 确定). Focus moves into the first field, stays trapped inside, and returns to the trigger on close. While submitting, the primary button shows loading; a failed validation keeps the dialog open. Title and footer stay fixed while the content scrolls.
- Feedback: toasts at top centre for about 3 seconds, at most three at a time.
- Pickers: selects with more than about ten options get search; multi-select overflow shows +N; the placeholder is 请选择. Dates use YYYY-MM-DD with a clear button and quick ranges. Money inputs have a ¥ prefix, two decimals and no steppers.
- Frame: the sidebar collapses to icons with hover names and collapses automatically on narrow screens. Breadcrumbs appear only on pages deeper than one level. The avatar opens the account menu.
- Charts: the tooltip follows the hovered point, titled by the dimension value, one row per series with colour dot, name, value and unit, and the whole group shown for a shared x value.
- Avatars are round for people and square for stores, with the first character when there is no image. Status tags pair colour with at most six characters of text. Badges show 99+ above 99, or a dot when only presence matters.

## Session sequence

0. Read `experience/catalog.md` and run `experience.py search --industry <行业> --surface <端> --text "<关键词>"`. Start from matching functions, components, palettes, type scales, and rules instead of re-deriving them.
1. Record every user request in BRIEF as a stable REQ-ID with module and acceptance signal.
2. Create the module intake and wait for a human module approval. Scripts and the model never approve.
3. Reuse fresh experience sources first (`experience.py reuse <session> SRC-…`, valid for 180 days), then run LuzCrawl (`D:\Codes\Luz-Crawl`, follow its SKILL.md: one `begin "<主题>" --new` task folder per request, `batch` for known pages, `search web` or on-site search for discovery) before writing anything. Research both the business (how products in this industry decide their core tasks and home page) and the specifications (typography, tables, navigation, layout) for the surfaces in scope. Research covers frontend references only: at least 12 unique URLs across 5 registrable domains, with at least 3 page-structure, 3 interaction-flow, and 2 component-state records. Snapshots are the LuzCrawl content records copied into `raw/`; HTTP status is measured live; a partial crawl counts only when its record confirms valid target content.
4. Write the frontend architecture: roles, functions, pages and routes, navigation, components and actions, interaction flows with recovery, interface states for every module, page data, traceability, acceptance. Inferred functions stay marked for confirmation.
5. After architecture approval: system design, then visual board, then interactive prototype, each with its own human approval. Exercise the prototype in a browser and save the acceptance screenshot.
6. Publish the final HTML: `publish.py <session> <stage>`.
7. Sediment the session: `experience.py harvest <session> --industry <行业>` extracts sources, functions, flows, and the palette; `experience.py add <file.json>` records judged knowledge — reusable components, design ideas, frontend rules, type-scale facts, and research lessons. Every project leaves the library richer.

~~~powershell
py -X utf8 scripts/experience.py search --industry "<行业>" --surface 小程序 --text "<关键词>"
py -X utf8 scripts/new_session.py --name "<session-name>" --modes system --system-name "<exact-system-name>" --modules "<module-1>,<module-2>"
py -X utf8 scripts/experience.py reuse "<session-folder>" SRC-001 SRC-002 --module "<module>"
py -X utf8 scripts/add_mode.py "<session-folder>" visual
py -X utf8 scripts/add_mode.py "<session-folder>" prototype
py -X utf8 scripts/publish.py "<session-folder>" prototype
py -X utf8 scripts/experience.py harvest "<session-folder>" --industry "<行业>"
py -X utf8 scripts/experience.py add "<knowledge.json>"
~~~

Every approval records status, relative artifact path, SHA-256, time, approver, and note in `raw/99-delivery/APPROVALS.json`.

## Imagery with the local image service

Interfaces need real imagery. Use `D:\Codes\Imagegen\src\imagegen.py`; every request is billed.

1. Write one prompt file per image under `raw/02-visual/prompts/` from `references/prompt-image.txt`, sharing a style block (light, theme colours, no text, no logos, no identifiable faces); dry-run first.
2. Send one request at a time. Parallel requests timed out in practice; a timeout gets one retry, then fall back to vector illustration instead of retrying again.
3. Use the image service only for photos of stores, products and environments. Icons and illustrations are drawn as flat line vectors (design-standards.html: 扁平线性风格); do not generate 3D icon sheets or background textures.
4. Review every image before use; crop compositions that came out wrong; record the image keys used by the page.

## Integrated system design page

When the user asks for one page holding the function list, an operable mini-program, and the admin console, build it as `raw/03-prototype/interactive-prototype.html` with exactly three parts: `系统功能列表`, `小程序界面`, `后台管理界面`, then publish it as the final HTML. Generate the function list, page IDs, and action IDs from the same specification as the architecture so every button carries an approved action ID.
