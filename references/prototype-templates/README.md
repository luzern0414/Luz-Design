# 原型参考实现与组件模板库：方案与目录结构

本页是方案与分工的单一出处。要做“产品开发用的前端界面 HTML”（小程序、后台、多个系统）时，从这里开始；做法的细则在各子目录的文档里，规则的强弱与偏离写法沿用 `page-patterns.json` 的 `method`。

## 零、定位：参考，不是写死的模板

本目录（路径仍叫 `prototype-templates`）里的东西**只供参考**。行业不同，首页的功能、模块和布局就不同；页面清单、首页组成、入口、标签栏、流程都由项目自己的功能说明（Luz-System 的功能清单与入口表）和行业决定，再用页面范式库选范式——不从这里的示例继承。

- **可以直接拿来用的是机制**：页面栈、标签栏与导航栏的外壳、配置面板（主题色、图标风格、外观、场景、全局）、逻辑面板、规格校验和生成器。它们与行业无关，需要时整套用，也可以只取其中一块，或者照着思路自己写。
- **只能当参考的是内容和结构**：示例里的页面清单、首页的模块顺序、入口、文案、数据、商品，都是某个行业的一种答案，不是默认值；不要因为示例有“购物车”“订单”就给每个项目加购物车和订单。
- **规格里除了引用关系必须成立（页面存在、返回目标存在、标签页不被 go 指向等）之外，没有任何必填的页面或模块**；校验器只查结构，不查行业内容。
- **示例有好几份、行业各不相同**，就是为了让人看到同一套机制可以长出不同的首页和页面组成；生成新原型时先问“这个行业的用户第一件事是什么”，再从页面范式库和组件库里挑，不是先挑示例。
- 组件模板库同理：303 个带编号的组件是积木和参照写法，按场景挑、改、组合；编号让你和别的会话能准确指同一个组件，不是要求每个页面都用库里的组件原样拼出来（`custom` 页面可以自己写，只要用的是库的积木并保留 `data-cid`，或在偏离说明里写明为什么没用）。

## 一、交付物的形态

产品开发阶段交付的前端界面 HTML，可以做成“花店小程序”那种样子（这是目标形态，不是固定结构）：

- 三栏单文件原型：左栏有页面目录、外观配置（主题色、头部背景、图标风格、图标底）、场景开关；中间是手机框或浏览器框，页面栈导航真实可点（标签只由标签栏切换、二级页隐藏标签栏、返回到来源、流程完成回到发起处）；右栏是“本页逻辑”（来源、返回、完成后、主操作、规则、状态、后台维护）、业务规则和状态流转。
- 交互完整：点击、滑动、切换、弹层、表单校验、状态变化都做出来；主题与图标可配置；手机宽度（390）可完整操作，无横向撑破。
- 多个系统就多个页签：一份文档里“前端架构”页签加每个系统或设备端一个页签，每个页签只放一个可交互原型。
- 页面由组件模板库里带编号的组件拼装，组件库本身也在仓库里。

机制里没有任何行业语义（不留“花店”“花间集”）；花店小程序只是由这套机制、一份规格和一个内容模块生成的一个行业示例。

## 二、七个技能谁负责什么、哪里引用哪里

一条规则只留一处；别处只指向它。

| 技能 | 负责什么 | 不负责什么 | 引用关系 |
|---|---|---|---|
| Luz-Design | 视觉与交互的外观；原型模板、组件模板库、渲染机制与配置面板；页面范式库、图标背景卡片规范 | 页面该有什么功能与业务规则；后端；验收与发布 | 读 System 的功能说明与入口表；把令牌与组件编号交给 Dev |
| Luz-System | 功能结构、页面清单、流程、状态、业务规则、入口唯一与首页分层的功能规则 | 视觉、动效、构图、图标、卡片 | 模板的“逻辑面板”只渲染 System 提供的数据，规则不在 Design 重写；功能规则见 System 的界面通用规范 |
| Luz-Dev | 后端、接口、数据库、部署，把已批准的界面接成真实系统 | 视觉与页面功能的改动 | 只消费设计令牌和“组件编号到实现”的对应，不依赖模板代码 |
| Luz-Ops | 验收测试、发布门禁、监控、回滚 | 设计与实现 | 可借用原型的交互检查思路，检查脚本不进模板 |
| Luz-Project | 阶段、审批、文档编排；`02-前端界面设计.html` 的章节与校验 | 视觉规则与模板内容 | 文档要求里指向本模板与多系统外壳；校验器认本模板产出的原型（见第六节） |
| Luz-Writing | 文字：文案、协议、说明 | 排版与界面 | 不改 |
| Luz-Crawl | 搜索与采集 | 其余 | 不改；前置检索按全局协议 |

## 三、与已有的东西是替代还是补充

| 已有 | 关系 |
|---|---|
| `references/ui-kit/`（令牌、六种布局、`ui.js`、`commerce-kit`） | 补充，不替代：它是行业无关的视觉底座与六种页面布局的参照写法；新模板的页面范式取 `page-patterns`，组件取新库；`commerce-kit` 的示例保留 |
| `references/component-libraries.json` 里的 Element Plus、Vant 等 | 并存：要接真实代码用它们；要出带编号、可直接演示的原型用新库（登记为 `luz-kit`）。同一个原型只选一个库 |
| `scripts/audit_rendered.py --library` | 补充：对 `luz-kit` 按组件根上的 `data-cid` 核对，每个控件必须落在带编号的组件里 |
| `scripts/make_showcase.py` | 无关：它做的是 PDF 架构图册 |
| Luz-Project 的 `prototype` 块 | 对接：生成的原型文件可直接放进 `02-前端界面设计.html` 的各前端页签 |

## 四、目录结构

```text
references/
  component-library/            组件模板库（编号取用）
    README.md  SPEC.md           取用方法与开发规范
    src/                         全部源码：taxonomy / core-def / core-ui / extras / ix / kit / combo / blocks-*.js / lib.template.html
    assets/                      WebP 素材：icons/{3d,real,flat}、products、bg（合计约 0.4 MB）
    build.py                     在仓库内重新构建单文件库（输出 dist/，不入库）
    registry/index.md            编号索引（按编号查名称、风格、适合与避免）
  prototype-templates/
    README.md                    本页
    engine/                      两个模板共用：页面栈、配置面板、逻辑面板、场景、外观、演示数据工具
    mini/                        小程序模板（模板 HTML、运行时、示例）
    admin/                       后台模板
    schema/prototype.schema.json 原型规格的结构与校验
    examples/                    generic-mini / generic-admin（通用）、florist-mini（花店示例）及其素材
scripts/
  build_component_library.py     构建组件库（包装 build.py）
  check_component_library.py     库完整性：编号唯一连续、作用域前缀、每类有“怎么选”
  build_prototype.py             规格 JSON → 单文件 HTML（mini 或 admin）
  build_prototype_suite.py       多系统外壳：前端架构页签 + 每个系统一个页签
```

## 五、原型规格（spec）

规格是一份 JSON，字段与 Luz-System 的界面功能说明对齐：

| 规格字段 | 对应 System 的 | 在原型里渲染到 |
|---|---|---|
| `pages[].logic.from` | 页面的进入来源 | 右栏“来源” |
| `pages[].logic.back` | 返回目标 | 右栏“返回”，也是页面栈返回的落点 |
| `pages[].logic.done` | 流程完成后去哪 | 右栏“完成后” |
| `pages[].logic.primary` | 本页主操作 | 右栏“主操作” |
| `pages[].logic.rules / states / backend` | 业务规则、五类状态、后台维护项 | 右栏相应小节 |
| `flows[]` | 流程 | 左栏“场景”里的流程直达 |
| `statuses[]` | 状态机 | 右栏“订单状态”类面板 |
| `tabbar[]` / `nav[]` | 标签栏 / 侧栏菜单 | 手机框的标签栏 / 后台的侧栏 |

页面内容有两种写法，可以混用：`blocks`（按组件编号拼装，可对组件里的文字、图片、跳转做覆盖）和 `custom`（引用内容模块里的渲染函数，用于库里没有的专属页面，渲染里仍要用库的组件当积木，并在页面上标 `data-cid`）。

## 六、对接与硬要求

- Luz-Project 对原型的硬检查（文件不小于 120 KB、有“减少动态效果”分支、对话框带角色、有场景配置面板、用到库的组件不少于 6 种）由模板自带满足；校验器认的标记以 `references/dev-documents.md` 为准。
- 配置面板的内容：外观（跟随系统、浅色、深色）、主题色、头部背景（小程序）或侧栏深浅与密度（后台）、图标风格、图标底；场景逐一列出成功、处理中、每种失败原因、加载、空、禁用、无权限；全局含网络、减少动态、角色、重置演示数据。
- 视觉：低饱和（状态色用 SPEC 里的固定低饱和色）、一条字体栈、字重 400/600/700（700 仅 22 像素及以上）、不斜体不加字距、控件图标线性 2 像素、头像用卡通动物不用文字、后台详情与编辑用居中面板不用右侧抽屉。
- 手机宽度 390 可完整操作，无横向页面滚动；文本框聚焦不出现蓝色或主色选中框。
- 图片只用 Imagegen 生成的素材；通用模板与示例里不留行业专属字样。

## 七、验收

每个模板与库组件都要有 Playwright 实测，不通过不算完成：生成器（规格→HTML 能构建、坏规格报错）、库完整性（编号唯一连续、作用域前缀、每类有“怎么选”）、交互抽样（各类组件点一遍、控制台零错误）、原型流程（页面栈、标签栏、返回、配置面板、场景、逻辑面板）、390 与桌面宽度、深浅两种外观。没有浏览器时对应测试跳过并写明。
