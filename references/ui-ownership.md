# 界面职责划分：功能归 Luz-System，视觉归 Luz-Design

适用于所有产品前端（网页管理后台、小程序、手机网页、网站、智能体界面）和它们的原型。本页规定已明确项目的职责边界；用户当前要求及 design/hard-rules.md 优先。独立前端任务可从用户请求形成简报并实施，不以缺少 System 文件阻止已授权工作。

## 默认组件复用与显式严格模式

默认 component-reuse：已有项目复用 System 定义的需求、页面、动作、数据、权限、状态和组件能力；Design 先核对已确认的设计和组件，依据不足时按共同证据合同调查，然后选择框架和成熟组件。统一适配文字、颜色令牌和图表/配置数据；在已定功能与语义顺序内组合组件，按授权任务实现业务事件；复杂控件优先成熟组件，必要自研记录理由和验证，不额外增加审美审批。完整行为和整页一致性共同验收。显式 source-locked 继续仅改允许文字，不混用证明。 具体执行见 [component-reuse.md](component-reuse.md)。UX、DX、AX 要用任务结果、可复现构建与可观察动作验证；AX 不是无障碍的别名。

## 一句话

Luz-System 决定页面内容、模块的上下阅读顺序、业务重心、每个控件的功能与办理结果。Luz-Design 决定如何用视觉层级、组件、栅格、字阶、色彩、留白与动效把这份功能说明呈现出来。

相关功能的主入口与跨页快捷入口以 System 的[入口归属规则](../../Luz-System/references/ui-standards.html#entry-ownership)为准。Design 按已确认的入口组织页面，Dev 在所属业务流程实现规则，Ops 从主入口和快捷入口分别验证结果。

同一个页面，System 写清它有哪些入口、标签栏有几项、用哪些组件、每个按钮做什么；Design 把这些画出来：构图、卡片、按钮的样子、图标、配图、动效、主题。

标签根页从交接表中的第一个业务模块开始。交接里的页面名称用于识别路由和核对入口。成品按[标签落地页规则](design/hard-rules.md#界面导航)处理首屏及可访问名称。

## 对照表

| 事项 | Luz-System 决定（功能） | Luz-Design 决定（视觉） |
|---|---|---|
| 页面与入口 | 有哪些页面与路由；每个功能的类别（核心、信息、营销、辅助）和唯一入口归属（标签栏、桌面侧栏、首页、个人中心、页内）；每个入口去哪 | 入口怎么排、图块的样子 |
| 首页 | 确认角色、当前主任务、模块阅读顺序、第一眼需要看到的信息、各入口的落点与效果 | 按该顺序和重点安排版面、视觉分组、对齐与密度，核对渲染后的入口去重 |
| 标签栏与导航 | 标签栏几项、叫什么、顺序、默认项、哪些页面显示；侧栏菜单分几组、层级关系；返回规则 | 标签栏的高度、图标图形、选中样式；侧栏的宽度与分隔；导航栏的样子 |
| 组件 | 用哪些组件承担哪个任务（表格、筛选、表单、对话框、步骤……）；它们的行为、状态、键盘操作、可访问名称 | 选哪个组件库、主题怎么接；组件的外观、尺寸、圆角、颜色 |
| 按钮 | 哪个动作放按钮；一个动作一个按钮；文案（动词加对象）；何时可用、何时禁用并写什么原因；点了以后的结果、反馈、确认与撤销；谁有权限；这页的主动作是哪个 | 主、次、危险按钮长什么样；尺寸、圆角、图标选哪个图形；悬停、按下、禁用、加载的外观 |
| 卡片 | 卡片承载哪些内容、按什么顺序；整卡点了去哪；卡里有哪些操作 | 卡片的构图与层次；圆角、描边、阴影；卡内图文的比例与对齐 |
| 列表与表格 | 有哪些列、默认排序与视图、筛选项、分页方式、批量操作、导出范围 | 列宽、对齐、行高、表头样式、斑马线、密度 |
| 图表 | 回答什么问题、用哪些指标、按数据关系选哪类图、数据少时怎么降级 | 配色、线宽、网格、提示框、图例的样子 |
| 有序状态（有先后顺序的状态集合：沟通深度、轮次、过程环节） | 集合里有哪些状态、先后顺序、管理员能否增减与排序、哪些是终态（成交、流失这类结果），写成 `states[].ordered`、`order`、`terminal` | 同页多个取值时的颜色：色阶、取色依据、令牌、文字 / 圆点 / 标签的样式，图表分段与图例的颜色；终态用状态色令牌 |
| 图片与插画 | 哪些对象要有图（商品封面、门店照片、空状态配图的位置）；图缺失时的降级 | 依已确认用途选择素材与表现方式、比例与裁切；插画与封面 |
| 图标 | 哪个功能需要图标；一个对象一个图标（含义不重复） | 图标集、线宽、双色块、尺寸、选哪个图形 |
| 动效 | 哪个操作要有反馈；变化不许让周围内容跳位；可撤销的时限；减少动态效果下保留什么 | 动画的形态、时长、缓动、转场、骨架与加载的样子 |
| 响应式 | 窄屏上哪些功能保留、哪些收进“更多”；手机上必须能完整操作 | 断点、栅格、列数、间距、各档怎么排 |
| 主题 | 是否需要外观设置、支持哪些主题、默认值及入口 | 已确认主题的取值与对比度；需要切换时不闪不跳，不为无需求页面增加主题 |
| 文案 | 按钮、提示、状态的文案键表与含义 | 字体、字号、行高、字重（文风归 Luz-Writing） |
| 原型 | 动作编号、页面编号、状态与演示数据、场景配置面板、减少动态效果开关 | 原型的全部外观：组件库、主题、配图、动效 |

## 交接物

### 逐页视觉交接

按同一页的功能编号核对三件事。先按 System 给出的阅读顺序排出各组，明确第一眼应看清的对象、状态或决定。再逐个对应按钮、文字、选项、卡片、图片和数据来源，区分展示、填写、触发动作。最后用真实长短内容走一次主路径与适用的失败恢复，核对视觉、键盘和辅助技术的阅读顺序。新编合同的字段见 [System 页面结构与控件](../../Luz-System/references/handoff.md#页面结构与控件)。

同一组可以用对齐、留白或底色来聚合，也可以使用已有卡片。宽屏在同一阅读层次内可并排，窄屏按交接顺序展开。控件如何画、换用哪一个等效组件由 Design 决定。若要改变 Tab 目的地、字段必填条件、按钮承诺、业务图片用途或哪个模块优先，先由 System 更新该决定。独立视觉任务从用户简报或现有页面取得功能清单，按明确范围直接工作。

**System 交给 Design 的是“界面功能说明”**：页面清单与路由、入口、标签栏项数与名称、每页的组件清单与用途、动作表（动作编号、按钮文案、触发与禁用条件、结果与反馈、确认与撤销、权限）、状态、数据需求、文案键。项目模式里它是系统架构阶段登记的随附产物（`界面功能说明.html` 与已登记的界面合同，受哈希保护，见 Luz-Project `references/dev-documents.md`），架构文档本身不设前端页签；独立会话里它是架构与系统设计网页。里面不出现颜色、字号、圆角、阴影、图标图形、图片内容、动画时长和栅格数值。有先后顺序的状态集合（沟通深度、轮次、审批与订单的过程环节）要在状态里写成一份有序集合：每个状态的名称、顺序、管理员能否增减与排序、哪些是终态；来源锁定任务仅核验来源已有状态，不改色阶、添加或排序；默认组件设计按它的顺序位置取色阶。

**入口表 `entrances.json`** 由 System 交付。入口含义、格式和默认位置从 [System 入口归属](../../Luz-System/references/ui-standards.html#entry-ownership)及其 `entrances_check.py --schema` 读取。Design 的 `page_pattern.py brief` 导入同一个校验器。已有首页的入口变更先由 System 确认，再在 Design 方案中调整可见布局和组件。

**来源锁定交接**：完整来源文件树、抓取和版本许可证据、原件及资产哈希、允许文字补丁、回执与当前真实浏览器报告；不重新导出主题或改资产。

**组件设计的交接是“视觉规范与完整复用包”**：所选组件库与主题、设计令牌文件（`export_tokens.py`）、视觉板、原型的外观、图标与配图的资产清单、动效令牌与场景表。开发技能按它实现。组件计划及 System 需求哈希、来源/许可、适配、当前浏览器与整体审阅一起交接。

**原型**：行为、数据和场景由功能说明规定；外观、组件库和动效由视觉规范规定。项目模式里原型和前端界面设计文档由 Design 阶段交付；独立会话里视觉板和原型的外观部分按 Design 的规则卡产出。

### 逐模块核对与经验

先按入口走一次真实页面。使用 System 的 `ui_requirements.py <合同> --entry <入口编号>` 核对每条分支的页数、顺序、返回和每页承载的内容。首屏先辨认对象和状态，中间按依赖分组，对应位置显示动作与结果。选择列表很长时保留对象摘要、明确选中项，并让主操作在目标设备可达。短确认、字段错误、加载或受理反馈可以在当前页面呈现。跨角色交接从下一位自己的入口继续。逐页用真实长度的字段走通一遍，核对键盘焦点、手机滚动及回到原对象后的结果。页面数量与分区位置随任务而定。

按业务模块接手。一个模块可以跨页，同一页也可服务多个模块。拿到新版 System 合同，可在 System 技能根运行 `py -X utf8 scripts/ui_requirements.py <合同> --module <模块编号>`。独立任务用简报或当前产品确定同样的信息。视觉设计据此逐项核对。

| 模块内的事项 | 视觉如何承接 | 可以交给 Luz-Crawl 的问题示例 |
|---|---|---|
| 功能逻辑 | 核对当前角色和首要任务，区分可操作、只读和无权状态。 | 同类组件怎样让用户辨认“可提交”和“仅可查看”？ |
| 数据结构 | 采用上游字段含义、关系、单位和缺失含义，实际排一次零值、长值与空值。 | 官方组件怎样并列展示带单位的数值和未知值？ |
| 布局 | 按业务依赖组织阅读顺序。选择宽窄屏的排列、字阶、分组和间距。 | 同类产品在窄屏如何让两个待比较字段仍能逐项对照？ |
| 交互 | 为既定动作呈现默认、聚焦、提交中、结果和可恢复错误，核对结果出现在对应对象旁。 | 官方组件如何显示可被键盘定位的字段错误？ |
| 流程 | 按真实角色走完入口、提交、接手和结果回看。检查每步能否辨认进度、结果和下一步。 | 异步受理后，公开实例怎样区分“已收到”和“已生效”？ |

开始用 `experience.py search <模块名> <问题>` 查[已有经验](../experience/catalog.md#按模块查经验)。用户要求联网或本地依据留有缺口时，把模块、维度和问题交 Luz-Crawl；同一需求共用采集目录，分别记录原文或截图、结论采用在哪个控件，以及什么情况下不适用。研究发现涉及字段定义、权限或状态变更时提给 System 确认。

完成一次验证后，用 `experience.py note` 记录已证实的视觉做法或失败原因。经验键用“模块-模块名-维度-问题”，依据写所测设备或页面、原文或观察结果和适用条件。项目专用结论用 `--scope project`，下次查回后以当前设备、品牌和任务复核。命令自动更新同一个 Markdown 目录。

## 两条不许越过的线

1. **System 不选视觉**。规格里只写“需要什么”（“商品卡要有封面图”“标签栏 4 项”“这个按钮在库存为 0 时禁用并写原因”），不写颜色、字号、圆角、阴影、描边、图标图形、配图内容、栅格与间距、动画时长与缓动。规则页里需要这些数值的地方，写“见视觉设计规范某节”。
2. **Design 不改功能**。页面、入口、标签栏项数与顺序、组件有无、按钮有无及其动作、流程、状态、文案键，Design 只能照做。画不下、排不下时，不自行增删，退回 System 提变更（项目模式走需求变更台账）。

来源锁定任务以保留原件为约束：功能不匹配就另选已核验完整来源或记录缺口；文字过长就缩短允许文案。不改外观、几何、组件或状态来补功能。默认组件设计可调整统一布局与允许适配，不能改业务含义；既有维护只在明确范围内处理冲突。

## 容易划错的几处

- **时间**：提示 3 秒后消失、删除后 5 秒内可撤销、加载超过 1 秒才出骨架、点击 0.1 秒内要有反应，这些是行为，归 System；动画跑多久、用什么缓动，是视觉，归 Design。
- **可访问**：键盘能到、角色与状态、可访问名称、悬停内容的触屏替代，归 System；焦点框的样子、触控目标的尺寸、文字对比度的取值，归 Design。
- **主动作**：这页的主动作是哪个，是功能优先级，归 System；它画成实色主按钮，归 Design。
- **窄屏**：手机上还能不能做完这件事，归 System；怎么排，归 Design。
- **头像**：有没有头像位、没头像时是否显示默认头像，归 System；头像怎么画，归 Design。
- **有序状态**：有哪些状态、谁先谁后、能不能由管理员增减、哪些是终态，归 System；这些状态在同一页里用什么颜色区分、颜色怎么随顺序递进、数量变了怎么重取、终态为什么用状态色，归 Design（`visual-design.html` 有序进度状态的色阶）。判断：把两个状态的先后换一下，用户能做的事会变吗？会变是功能，不会变只是颜色跟着位置走。

## 商业项目交接

design 阶段核对已确认范围与 System 的页面、权限、动作、字段与异常合同。在前端开发说明写清导航、关键组件、目标端、接口与反馈，由 Dev 确认接口和状态。功能、技术、前端和后端说明一同确认。沿用当前项目框架与可复现组件，复杂控件自研注明调查过的来源、业务缺口与针对性验证。

第二批确认后在 demo 阶段交付 `docs/03-开发资料/05-交互原型.html`。按功能编号配齐各岗位的业务入口、查询筛选、对象详情、操作表单、复核队列与关联记录。一次提交同时更新列表、详情和相关数量。查询功能以实际检索值和命中的对象复核，办理功能以操作后的状态和流水复核。数据与外部服务的模拟范围在环境入口标明。用户走查后按功能编号登记反馈，业务范围变化交给 System 与 Project。第三次确认后将界面合同、操作记录和工程约束交给 Dev、Ops。
